# Décisions techniques — Jalonia SaaS

Ce fichier garde la trace des choix d'architecture et de leur raison, pour que personne n'ait à les deviner.

| Date | Décision | Raison |
|------|----------|--------|
| 2026-10-11 | **TypeScript de bout en bout** : Next.js 16 (App Router), Node.js | Un seul langage pour tout ; réutilise la logique du moteur Qualigramme (JavaScript). |
| 2026-10-11 | **PostgreSQL auto-hébergé** sur le VPS | Maîtrise des données ; pas de dépendance à un service tiers. |
| 2026-10-11 | **Auth.js v5** (`next-auth@5.0.0-beta.32`, version figée) | Demandé par Brice. La v5 reste étiquetée « beta » mais elle est maintenue et compatible Next 16 ; version figée pour éviter une mise à jour imprévue. |
| 2026-10-11 | **Schéma PostgreSQL par organisation** + **rôle PostgreSQL par organisation** | Isolation « étanche » : chaque requête d'une organisation s'exécute avec `SET LOCAL ROLE org_xxx_rw`, rôle qui n'a de droits que sur son propre schéma. Une erreur de code ne peut pas lire le schéma d'une autre organisation : PostgreSQL refuse. |
| 2026-10-11 | Rôle applicatif `jalonia_app` membre des rôles d'organisation **sans héritage** (`WITH INHERIT FALSE, SET TRUE`) | Sans `SET ROLE` explicite, l'application n'a AUCUN droit sur les schémas d'organisation (échec fermé). |
| 2026-10-11 | Rôle `jalonia_owner` réservé aux migrations et à la création d'organisations (*depuis le 12/10 : migrations et création d'un superadmin seulement ; voir « Création d'une organisation sans le rôle propriétaire »*) | L'application courante n'a pas le droit de créer des schémas ou des rôles. |
| 2026-10-11 | **Migrations SQL écrites à la main** (une seule source de vérité) + **requêtes SQL paramétrées** (`pg`, `$1`, `$2`…) — **pas d'ORM** | Les rôles, droits par colonne et déclencheurs ne s'expriment pas avec un ORM. Drizzle (envisagé au départ) génère des `INSERT` qui nomment toutes les colonnes, ce qui casserait les **droits par colonne** (ex. : l'application n'a pas le droit d'écrire `est_superadmin`). Les identifiants dynamiques (schéma, rôle) ne passent que par une fonction qui les valide par expression régulière. |
| 2026-10-11 | **Droits par colonne** pour le rôle applicatif | L'application ne peut ni créer ni promouvoir un superadmin, même en cas de bogue ou d'injection : seule la commande d'installation (rôle propriétaire) le peut. |
| 2026-10-11 | **Journal d'audit en ajout seul** (déclencheurs qui refusent UPDATE, DELETE, TRUNCATE ; droits SELECT/INSERT seulement) | Traçabilité inaltérable des opérations sensibles. |
| 2026-10-11 | Sessions Auth.js en **JWT** + table `platform.sessions` vérifiée à **chaque requête** | Le fournisseur « identifiants » d'Auth.js impose le JWT ; la table permet de suivre la durée, l'adresse IP et de **révoquer** une session. |
| 2026-10-11 | Mots de passe **argon2id** (19 Mio, t=2, p=1 — recommandations OWASP), verrouillage 15 min après 5 échecs | Standard actuel de stockage des mots de passe. |
| 2026-10-11 | **Un seul nom de domaine** ; l'organisation active est déduite de l'adhésion de l'utilisateur | Évite les certificats « wildcard » et la configuration DNS par client. |
| 2026-10-11 | `cacheComponents` **désactivé** (option de Next 16) | Application d'administration entièrement dynamique ; ce mode impose des contraintes (frontières `<Suspense>`, erreurs de compilation sur la lecture des cookies) sans bénéfice ici. **À adopter lors du passage à Next 17**, où il deviendra le comportement par défaut. |
| 2026-10-11 | Le proxy (`src/proxy.ts`) ne fait qu'une redirection « optimiste » ; **chaque page et chaque action serveur revérifie** l'authentification et les droits | Recommandation explicite de la documentation Next.js 16 (Data Security). |
| 2026-10-11 | Police Outfit **embarquée** (pas de téléchargement Google à la compilation) | Compilation sans dépendance réseau externe. |
| 2026-10-11 | Alerte `npm audit` sur `braces` (via `eslint-config-next`) **acceptée** | Concerne uniquement l'outil de vérification du code, jamais l'application en production ; aucune version corrigée n'existe. `npm audit --omit=dev` = 0 vulnérabilité. |
| 2026-10-11 | **Aucune route `/api/auth`** : connexion et déconnexion passent par des actions serveur qui appellent Auth.js | Surface d'attaque réduite (pas de pages ni de points d'entrée Auth.js exposés). |
| 2026-10-11 | Message d'échec de connexion **unique** (mauvais identifiants, compte verrouillé ou désactivé) ; temps de réponse égalisé pour un e-mail inconnu | On ne révèle pas quels comptes existent. Le motif exact est dans le journal d'audit. |
| 2026-10-11 | Comptes **superadmin gérés en ligne de commande uniquement** (`scripts/creer-superadmin.ts`) ; l'interface ne peut ni désactiver, ni réinitialiser un superadmin, ni agir sur son propre compte | Un compte superadmin compromis ne peut pas évincer les autres. Le script sert aussi à retrouver l'accès. |
| 2026-10-11 | Seul le superadmin peut **réinitialiser un mot de passe** (pas l'administrateur d'organisation) | Une personne peut appartenir à plusieurs organisations : l'administrateur de l'une ne doit pas pouvoir prendre le contrôle d'un compte qui donne accès à une autre. |
| 2026-10-11 | Nouveaux comptes avec **mot de passe provisoire** transmis hors application, changement **obligatoire** à la première connexion | Pas encore d'envoi d'e-mails. **Limite connue** : celui qui a fixé le mot de passe provisoire le connaît jusqu'au premier changement. À remplacer par des **invitations par e-mail** (lien à usage unique) quand le SMTP sera branché. |
| 2026-10-11 | Changement de mot de passe : l'erreur sur le mot de passe actuel **compte comme un échec de connexion** (verrouillage) ; les autres sessions sont fermées | Une session volée ne permet ni de deviner le mot de passe ni de garder la main après son changement. |
| 2026-10-11 | Désactivation d'un compte par le superadmin possible même s'il est le dernier administrateur d'une organisation | Départ d'une personne : la sécurité passe avant ; le superadmin désigne ensuite un nouvel administrateur. Les administrateurs d'organisation, eux, ne peuvent pas retirer ni rétrograder le dernier administrateur actif. |
| 2026-10-11 | Localisation des sessions = **adresse IP** (géolocalisation plus tard) | Une base de géolocalisation demande une licence et des mises à jour ; à ajouter avec l'incrément « Exploitation ». |
| 2026-10-11 | Garde-fous PostgreSQL sur `jalonia_app` : `search_path` vide, `statement_timeout` 30 s, `idle_in_transaction_session_timeout` 60 s | Défense en profondeur, en plus des réglages faits par l'application à chaque transaction. |
| 2026-10-11 | **Tests d'intégration sur un vrai PostgreSQL**, préparé avec le script d'installation réel (`deploy/preparer-base.sql`) | Les garanties d'isolation reposent sur PostgreSQL : elles se prouvent contre PostgreSQL, pas contre une imitation. |
| 2026-10-11 | Déploiement par **versions côte à côte** (`/opt/jalonia/versions/…` + lien `courant`), contrôle de santé et **retour arrière automatique** | La version en service tourne pendant la construction ; une mise à jour ratée ne coupe pas le service. |
| 2026-10-11 | Fuseau horaire d'affichage réglé par `FUSEAU_HORAIRE` (dates stockées en UTC) | Le serveur est à Toronto, les utilisateurs ailleurs : l'affichage suit le fuseau choisi. |
| 2026-10-12 | **Application installable** (manifeste web + icônes) : icône « Jalonia » sur le bureau ou l'écran d'accueil | Demande de Brice : ouvrir Jalonia « en tapant simplement Jalonia ». Sans nom de domaine court (achat à décider), c'est l'accès le plus direct, et il est gratuit. Pas de service worker : il n'est plus exigé pour l'installation et compliquerait l'authentification. |
| 2026-10-12 | Logo Jalonia d'origine : version claire dans le bandeau, version couleur sur les pages de connexion ; icônes, manifeste et logos servis **sans connexion** (exclus du filtre proxy) | Sinon le navigateur, non connecté, recevrait une redirection au lieu de l'icône ou du manifeste. |
| 2026-10-12 | **Incrément 2 : l'éditeur d'origine est repris tel quel** (`editeur/`, ses 445 tests compris), copié dans `public/editeur/` à la compilation, avec un **mode « en ligne »** posé par la copie (`<html data-mode="en-ligne">`) | Choix de Brice : aucune fonction de l'application d'origine n'est réécrite (donc aucune perdue). Le mode local reste intact et testé ; le mode en ligne ne change que la provenance et l'enregistrement des données. |
| 2026-10-12 | Contenu des documents et de la cartographie rangé en **jsonb**, sous la forme exacte des fichiers .json de l'éditeur | Un seul format partout (fichier, serveur, copie téléchargée). Le serveur contrôle la forme (objet, tableaux attendus, profondeur ≤ 32), la taille (**2 Mo**, comme les fichiers de l'éditeur) et retire ce que PostgreSQL refuse (caractère nul, demi-caractères) ; l'éditeur **nettoie champ par champ à l'ouverture** (`nettoyer()`), comme pour un fichier. Titre, code et type sont recopiés en colonnes pour la liste. |
| 2026-10-12 | **Enregistrement automatique** 1,5 s après la dernière modification, une seule requête à la fois, nouvel essai automatique (2 s → 30 s) en cas de coupure ; « Enregistrer » et « ← Mes documents » enregistrent tout de suite | Rien à penser pour l'utilisateur ; aucune requête par lettre ; une coupure réseau ne perd rien (le travail reste dans la page, alerte du navigateur avant de la quitter). |
| 2026-10-12 | **Verrouillage optimiste** : un numéro de version par document et pour la cartographie ; un enregistrement fait sur une version dépassée est **refusé (409)** ; la personne choisit « recharger » ou « garder ma version » (remplacement explicite, **toujours tracé** avec l'auteur remplacé) | Deux rédacteurs sur le même document ne s'écrasent jamais en silence. Pas d'édition simultanée en temps réel (hors de portée de l'incrément). |
| 2026-10-12 | Droits (décisions de Brice du 12/10) : **rédiger, supprimer, modifier la cartographie = administrateur et rédacteur** ; vérificateur, approbateur et lecteur = **lecture seule** (ouvrir, voir, exporter Word/PDF) | Le cycle vérification / approbation arrive à l'incrément suivant. La lecture seule est appliquée **par le serveur** (403) ; dans l'éditeur, le magasin défait toute modification et les champs sont non modifiables (confort, pas sécurité). |
| 2026-10-12 | Suppression **définitive** d'un document, après confirmation, **tracée** (titre, code, type, version) | Décision de Brice. **Limite connue** : pas de corbeille ; une suppression par erreur se rattrape seulement par la sauvegarde quotidienne de la base. À revoir avec le versionnage et l'archivage (cycle de vie). |
| 2026-10-12 | Journal : création et suppression toujours tracées ; enregistrements automatiques tracés **une fois par personne et par document toutes les 30 min** ; le journal de la **plateforme** reçoit les mêmes opérations **sans les titres** | Un journal lisible (pas une ligne par frappe) ; le superadmin voit l'activité sans lire le contenu des organisations. |
| 2026-10-12 | L'éditeur envoie l'organisation dans laquelle il a ouvert le document ; si une autre organisation a été ouverte dans un autre onglet, l'enregistrement est **refusé (409)** et expliqué | Sinon, avec le cookie d'organisation partagé entre onglets, le travail pourrait être enregistré dans la mauvaise organisation (cartographie surtout). |
| 2026-10-12 | Routes JSON de l'éditeur (`/api/editeur/contexte`, `/api/documents`, `/api/cartographie`) : **origine du site exigée** (en-tête Origin), type `application/json`, corps ≤ 2,5 Mo lu sans tout charger, session et droit revérifiés ; le proxy répond **401 en JSON** aux routes `/api/` sans cookie | Protection contre les requêtes forgées depuis un autre site, en plus du cookie SameSite=Lax ; l'éditeur reçoit des refus qu'il sait expliquer (pas une page de connexion). |
| 2026-10-12 | **Limitation des tentatives de connexion** (audit S2) : fenêtre de 15 min ; une adresse IP est refusée après 10 échecs (tous comptes) ; un couple (compte, adresse) après 5 échecs depuis sa dernière réussite ; un compte est verrouillé 15 min après 30 échecs toutes adresses confondues. Refus « sans calcul » tracés une fois par fenêtre. | L'ancien verrou par compte (5 échecs) permettait à n'importe qui de bloquer n'importe quel compte. Désormais un attaquant isolé ne bloque que lui-même ; seule une attaque répartie de grande ampleur verrouille un compte (et c'est tracé). Le journal, non purgeable, ne peut plus être inondé. |
| 2026-10-12 | **Calculs argon2id plafonnés** : 4 simultanés, 64 en attente, refus immédiat au-delà ; la vérification se fait **hors transaction** (lecture courte, calcul, écriture courte qui revérifie le compte) | Chaque calcul réserve ~19 Mio : sans plafond, quelques dizaines de tentatives simultanées épuisaient la mémoire du service (plafonnée à 700 Mo). Aucune connexion PostgreSQL n'est retenue pendant le calcul. Limite connue : sous un afflux venu de très nombreuses adresses, des connexions légitimes peuvent être refusées un moment (« réessayer ») ; seul un filtrage en amont (pare-feu, fail2ban sur le journal) l'éviterait. |
| 2026-10-12 | **Création d'une organisation sans le rôle propriétaire** (audit S1) : une fonction PostgreSQL `platform.provisionner_organisation()` (`SECURITY DEFINER`, appartenant à `jalonia_owner`) crée la ligne, le rôle, le schéma et les tables à partir des gabarits rangés en base par le lanceur de migrations ; l'application n'a que le droit de l'**exécuter** | L'application en service ne détient plus le mot de passe du rôle propriétaire : une faille d'exécution de code ne donne plus tous les droits sur la base. Sûreté de la fonction : nom de schéma vérifié par expression régulière avant tout SQL dynamique, identifiants cités, chemin de recherche figé, exécution retirée à `PUBLIC`, gabarits illisibles par l'application ; le lanceur refuse un gabarit déjà appliqué puis modifié ou supprimé. |
| 2026-10-12 | **Trois comptes système** (audit S0) : root lance le déploiement depuis **sa** copie du script (`/usr/local/sbin/jalonia-deployer`) ; `jalonia` récupère, construit et migre ; `jalonia-run` fait tourner l'application et ne possède rien | Avant, le service tournait sous le compte qui possédait son code et le script lancé par root : une faille d'exécution de code dans l'application devenait un accès root au déploiement suivant. Désormais le service ne peut modifier ni le code, ni le dépôt, ni les scripts, ni lire `/etc/jalonia`. Quand le script change dans le dépôt, `jalonia-deployer` s'arrête et demande de relire puis d'installer la nouvelle copie. |
| 2026-10-12 | Configuration en **deux fichiers** : `/etc/jalonia/jalonia.env` (root seul, lu par systemd) sans le mot de passe propriétaire ; `/etc/jalonia/proprietaire.env` (root et `jalonia`) pour les migrations et `creer-superadmin` | Le service ne reçoit que ce dont il a besoin. **Limite connue** : le compte de construction `jalonia` lit le mot de passe propriétaire (il lance les migrations) et produit le code servi ; un paquet npm malveillant installé à la construction aurait donc ces droits. Le réduire demanderait une construction isolée (conteneur, autre machine) : hors de portée pour l'instant. |
| 2026-10-12 | Service systemd durci : `ProtectSystem=strict` (aucune écriture nulle part), `CapabilityBoundingSet=` vide, `PrivateDevices`, `ProtectClock`, `ProtectHostname`, `ProtectKernelLogs`, `RestrictNamespaces`, `RestrictRealtime`, `RestrictAddressFamilies` (Unix, IPv4, IPv6, netlink), `SystemCallArchitectures=native`, `UMask=0077` ; **pas** de `MemoryDenyWriteExecute` (le compilateur JavaScript de Node en a besoin) ni de filtre d'appels système (`SystemCallFilter`, dont le contenu varie selon les versions de systemd et de Node : un oubli tuerait le service) | Réduit ce qu'une faille d'exécution de code permet. Vérifié sous un vrai systemd (255) : parcours navigateur complet, création d'organisation comprise, sans erreur. |
| 2026-10-12 | `jalonia-deployer --verifier` (et la fin de chaque déploiement) contrôle l'installation : compte du service, code et scripts non modifiables par lui, configuration illisible par lui, pas de mot de passe propriétaire transmis, copie de root intacte et identique au dépôt, application qui répond | Le durcissement se vérifie à chaque mise à jour, pas seulement le jour de son installation. |
| 2026-10-12 | **Optimiseur d'images de Next.js désactivé** (`images.unoptimized`) et `/_next/image` **refusé par le proxy (404)** | L'application n'affiche que des SVG, servis tels quels. Avec le service en lecture seule, l'optimiseur ne pouvait plus garder ses calculs en cache (erreur au journal et nouveau calcul à chaque requête : une porte ouverte à la saturation du processeur) ; même désactivé, Next.js tentait encore de créer son dossier de cache à chaque requête sur cette adresse. **À savoir** : si un jour l'application utilise la mise en cache de Next.js (pages régénérées, `use cache`), il faudra lui donner un dossier inscriptible (`CacheDirectory=` dans le service). |
| 2026-10-12 | **Politique de sécurité du contenu (CSP) sans script en ligne** (audit S7), posée par le proxy en production : pages = `script-src 'self' 'nonce-…' 'strict-dynamic'` avec un nonce neuf (128 bits) à chaque requête, que Next.js ajoute lui-même à ses scripts ; éditeur = `script-src 'self'` (il n'a aucun script en ligne) ; plus de CSP dans `next.config.ts` | Une injection de HTML, si elle existait un jour, ne pourrait plus exécuter de script : la CSP devient un second rempart. Vérifié : 21 pages visitées sous quatre rôles sans aucune violation ni script en ligne sans nonce ; parcours navigateur 1 à 5 sans erreur ; contre-épreuve dans une page et dans l'éditeur (gestionnaire `onerror`, lien `javascript:`, cadre `srcdoc`, script inséré) : rien ne s'exécute. |
| 2026-10-12 | Styles en ligne **toujours permis** (`style-src 'self' 'unsafe-inline'`) | React écrit des attributs `style`, et l'éditeur dessine ses SVG avec des attributs `style` : un nonce ne couvre pas les attributs (et sa présence annulerait `'unsafe-inline'`). Le risque d'un style injecté (mise en page altérée, fuite limitée) est bien moindre que celui d'un script. À reconsidérer si l'éditeur passe un jour aux classes CSS. |
